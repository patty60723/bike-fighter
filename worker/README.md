# bike-fighter API

網頁的後端，跑在 Cloudflare Workers 上，資料存在 Cloudflare D1（SQLite）。

| 路徑 | 用途 |
| --- | --- |
| `GET /stations` | 台北市＋新北市 YouBike 2.0 站點與即時車數（合併、去重） |
| `POST /anger` | 送出一批怒氣；伺服器檢查後才記錄 |
| `GET /stats?sid=&type=&device=` | 單站的怒氣統計、目前的空站魔王 |
| `GET /events?limit=` | 最近結束的空站／滿站紀錄（需求紀錄） |
| `GET /ntpc?page=` | 新北市原始資料轉發（舊版網頁用） |
| `GET /usage` | 今天（UTC）D1 用量估計、排程目前幾分鐘跑一次 |
| 每分鐘排程 | 依即時車數開始／結束空站、滿站紀錄 |

## 伺服器檢查的項目

`POST /anger` 會依序檢查，任何一項不過就不記錄：

1. 站點存在
2. 手速：點擊數不超過「連擊時間 ÷ 0.06 秒」
3. 冷卻：同一個裝置 30 秒內只能送一批
4. 移動速度：和上一批的位置相比，不超過每秒 30 公尺
5. 距離：在站點 100 公尺內（GPS 誤差最多再寬限 50 公尺）

通過的會記錄下來；當下站點真的是 0 輛（或 0 位）才標為「計入需求」。

已知限制：裝置代號是瀏覽器自己產生的，清掉瀏覽器資料就能換一個新代號、繞過冷卻。要擋這個需要登入帳號。

## 資料量

免費方案每天（UTC 午夜重置，台灣早上 8 點）上限：讀取 500 萬列、寫入 10 萬列（記憶值，以 Cloudflare 後台 **D1 → Metrics** 為準）。D1 的計算方式：寫入一列時，**每個索引也各算一列**；`AUTOINCREMENT` 的計數器也算一列；讀取算的是「掃過」的列數，不是回傳的列數。

### 排程（每分鐘）

v1.4 起，進行中的空站／滿站（`sid:type → 開始時間`）存在快照那一列的 `open` 欄位，跟站點清單一起寫，所以開始或結束一段空站**不用額外寫入**。只有真的要留紀錄的空站結束時，才寫一列到 `spells`。

| 每次排程 | 讀取 | 寫入 |
| --- | --- | --- |
| 讀上一分鐘的狀態（快照列＋最新怒氣 id） | 2 | 0 |
| 寫快照（站點清單＋進行中空站＋今日用量，一列） | 1 | 1 |
| 記錄結束的空站（有人受影響，或持續 5 分鐘以上） | 每段約 2 | 每段 1（有人受影響 2） |

- 恢復有車後要連續 3 分鐘才算結束（結束時間仍記第一分鐘），0 ↔ 1 跳動算同一段，不會開開關關。
- 本機量測（3,500 站假資料、每分鐘約 24 段開始／結束、55% 是 5 分鐘內的短暫跳動）：每分鐘讀約 63 列、寫約 12 列，**一天約讀 9 萬列（2%）、寫 1.7 萬列（17%）**。同樣情境舊版（v1.3）是一天寫 16.8 萬列；加上 0 ↔ 1 跳動時舊版 35 萬列、新版仍是 1.7 萬列。
- 依後台實際數字（v1.3 一天約 1.9 萬次開始、1.8 萬次結束，留下的紀錄約 8–9 千段）推算：新版一天約寫 **1 萬列（約 10%）**、讀 4–9 萬列（約 1–2%）。

`/stations` 直接讀這份快照，不用每次等兩個市府伺服器；快照超過 3 分鐘沒更新（排程放慢、D1 不能用）時才改成即時去問市府。

### 網頁（每個使用者）

| 請求 | 讀取 | 寫入 |
| --- | --- | --- |
| `/stations` | 0–1（每個 Worker 記憶體暫存 30 秒） | 0 |
| `/stats` | 約 10 ＋ 該站怒氣筆數 × 3（同一站 15 秒內共用） | 0 |
| `/events` | 最多 2 × limit（60 秒內共用） | 0 |
| `/anger` | 約 3 | 4（一列＋2 個索引＋計數器） |

`/anger` 每個裝置最多 30 秒一次，一個人一直打每分鐘最多寫 8 列；一般使用（一次來送幾批）每人一天幾十列。

### 自我保護

排程把今天估計用過的列數存在快照列的 `usage`（不多寫一列；`/anger` 的寫入從怒氣 id 的增加量估算），`GET /usage` 可以看。用量超前「一天 30%」的進度時自動放慢：

| 今天用量（讀、寫取比例高的） | 排程 |
| --- | --- |
| 低於 30% 的進度 | 每分鐘 |
| 超過進度，或達 30% | 每 2 分鐘 |
| 超過進度兩倍，或達 60% | 每 10 分鐘（快照超過 3 分鐘，`/stations` 改成直接問市府） |
| 達 85% | 暫停到 UTC 午夜，剩下的留給送出怒氣和統計 |

放慢時空站紀錄的時間精度變成 2／10 分鐘，不會漏記或重複記。同一個資料庫 30 秒內又被觸發一次排程（重複觸發、或另一個部署也綁了這個資料庫）會直接跳過；就算同時跑，快照的寫入有版本檢查，同一段空站也不會記兩次。

### 舊資料

- `empty_events`：v1.4 以前的紀錄，只讀不寫；`/stats`、`/events` 會把它和 `spells` 合在一起顯示。
- `empty_open`：v1.4 第一次排程會把裡面進行中的空站搬進快照，之後不再使用。確認新版正常後可以另外寫 migration `DROP TABLE empty_open`（不要用 `DELETE`，刪一列也算一列寫入）。**不要退回 v1.3**：舊版會用到過時的 `empty_open`。
- 不定期清舊資料：刪除也算寫入，表變大只影響單站查詢，現在用不到。

## 暫停服務（颱風等）

同一個城市有 50 站以上、而且超過六成的站同時是 0 輛時，判定為 YouBike 暫停服務。這段期間那個城市不開空站紀錄、不出現魔王，送出的怒氣也不計入需求；網頁把那個城市的站點畫成灰色。

## 超過 D1 每日上限時

免費方案超過每日讀寫上限後，當天剩下的 D1 查詢會失敗，到隔天（UTC 午夜，台灣早上 8 點）才恢復：

- 地圖車數照常顯示：`/stations` 讀不到快照時會直接去問市府；就算整個 API 掛掉，網頁也會改成直接讀市府資料。
- 送出怒氣、統計、空站魔王、需求紀錄會暫停，網頁顯示「即時資料・離線」。

`/stats`（15 秒）和 `/events`（60 秒）的結果會暫存在 Worker 記憶體，同一站的多個使用者共用同一次查詢；自己送出怒氣後，那一站的暫存會立刻清掉。workers.dev 網址不能用 Cloudflare 的 Cache API，要用的話需要自己的網域。

## 第一次部署

1. **建立資料庫**：Cloudflare 後台 → **Storage & Databases** → **D1** → **Create database**，名稱填 `bike-fighter`。
2. 複製資料庫的 **Database ID**，填進 `wrangler.toml` 的 `database_id`（已填好）。
3. **連接 GitHub 自動部署**：Workers & Pages → `bike-fighter-api` → **Settings** → **Build** → 連接 repo `patty60723/bike-fighter`：
   - Branch：`main`
   - Root directory（根目錄）：`worker`
   - Deploy command（部署指令）：`npm run deploy`
4. 之後每次推到 `main`，Cloudflare 會自動套用資料庫變更（`migrations/`）並部署。

## 本機開發

```sh
cd worker
npm install
npm run migrate:local
npx wrangler dev --test-scheduled
```

沒有網路可以抓市府資料時，在 `worker/.dev.vars` 放一行 `STATION_FIXTURE='[...]'`（站點陣列，格式同 `/stations` 的 `stations`），API 就會改用這份假資料。這個檔案不會被提交。
